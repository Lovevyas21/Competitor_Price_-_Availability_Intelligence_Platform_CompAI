# ADR-011: Write the infrastructure, do not apply it

**Status:** Superseded on 2026-09-09 -- see *Outcome* below.

## Context

Phase 6 of the build document calls for Terraform (RDS, EC2, S3, secrets, private
networking) and a GitHub Actions deploy. It is also the only phase that costs money:
roughly **$28–36/month (₹2,350–3,020)**, billed from the moment `terraform apply`
succeeds and continuing until the resources are destroyed.

Two further facts matter. The build document's own research notes that the AWS Free Tier
changed on 15 July 2025 — new accounts get a $100 credit plan that expires after six
months, **not** twelve months of free RDS. And nothing in the project needs AWS to be
demonstrated: the pipeline, marts, forecasts, API, matching and brief all run locally and
are covered by 150 Python tests and 102 dbt tests.

## Decision

**Write the complete infrastructure as reviewable code, and stop short of `apply`.**

- `infra/` holds the full stack: VPC with public/private subnets, RDS PostgreSQL
  (private, encrypted, TLS enforced), EC2 on Graviton, S3 bronze with lifecycle tiering,
  SSM Parameter Store secrets, least-privilege IAM, CloudWatch alarms and a budget alarm.
- Correctness is checked without an account: `terraform fmt`, `terraform init
  -backend=false`, `terraform validate` all run offline and are wired into CI.
- Deploy is `workflow_dispatch` only, behind a typed confirmation and a GitHub
  `production` environment. It cannot fire on a push.
- `terraform.tfvars` and state are gitignored; the S3 backend is present but commented,
  since it cannot exist before the first apply.

## Consequences

- The infrastructure is complete and reviewable — the part a reader actually evaluates —
  with no ongoing cost and no account required to check it out and validate it.
- **Unverified, and stated plainly:** `terraform plan` and `apply` have never run. Only
  the syntax and provider schema are confirmed. A first apply should be expected to
  surface real-world issues — AZ availability, RDS engine version drift, IAM propagation
  delays — that validation cannot catch.
- Several defaults are deliberately safe rather than convenient, and each costs
  something:
  - **No NAT gateway.** It would be ~$32/month, more than the rest of the stack combined.
    The consequence is that nothing in a private subnet can reach the internet; the
    workers run on the public-subnet host.
  - **SSH closed by default** (`ssh_ingress_cidrs = []`). Access is via SSM Session
    Manager, so there is no open port 22 and no key material. Convenient SSH requires an
    explicit CIDR.
  - **`deletion_protection = true` and a final snapshot** on RDS. `terraform destroy`
    will refuse until deletion protection is turned off — deliberate friction on the one
    irreversible action here.
  - **Budget alarm on forecast as well as actual.** By the time actual spend crosses the
    threshold, the month is already spent.
- Deploy uses **OIDC role assumption, not stored AWS keys**, and rolls out via **SSM Run
  Command rather than SSH** — no long-lived credentials in the repository, no inbound
  port.
- The database password is generated by Terraform and written to SSM. It is never
  emitted as an output: an output marked `sensitive` is still in state and still
  printable with `terraform output -json`.

## Outcome (2026-09-09)

The decision was reversed once AWS credits made the cost argument moot. Both stacks were
applied to a real account, the deployment reached the point of building and pushing an
image, and the infrastructure was then destroyed.

**Applying it found seven faults that `validate`, `plan`, 252 Python tests and every CI
gate had all passed.** That is the part worth recording, because this ADR originally
argued the configuration was reviewable without being applied, and the evidence says
reviewable is not the same as correct:

1. `db_engine_version = "16.6"` does not exist in ap-south-1. Region availability is a
   different list from "versions that exist", and neither `validate` nor `plan` consults
   it -- the failure arrives minutes into `apply`.
2. `db.t4g.micro` had no capacity in the region. Twenty minutes reporting only
   "creating"; the reason is not in the status field.
3. `deletion_protection = true` makes `terraform destroy` fail outright, and a fixed
   `final_snapshot_identifier` makes the *second* destroy fail because the name already
   exists. Correct for production, fatal for infrastructure meant to be disposable.
4. The image had no dbt, so the deployed host could ingest but never build the marts the
   API reads.
5. `ssm:GetParametersByPath` needs permission on the path node `/cpi/prod`, which
   `/cpi/prod/*` does not match. A trailing wildcard covers children, never the parent.
6. The instance role had no ECR permissions at all, and `ecr:GetAuthorizationToken` is
   account-level -- AWS accepts it only against `*`, so scoping it to the repository
   silently denies every login.
7. `alembic.ini` is parsed by configparser, which reads a bare `%` as interpolation
   syntax. RDS generates a password that URL-encodes to `%7B...%25`; the development
   password is plain, so migrations worked locally and could not run in production.

Only the first two are AWS-specific trivia. The rest are ordinary application and IAM
faults that no amount of static checking would have surfaced.

The infrastructure is now split into a persistent stack and a disposable one
(`infra/README.md`), driven by `make aws-up` / `make aws-down`, so the cost concern this
ADR was built around is handled by lifetime rather than by abstinence: idle cost is about
$0.30/month, and a demo costs roughly $0.035/hour while it is running.
