1Executive summary

The platform answers one operational question — who is undercutting us, on what, by how much, and how confident should we be in that — and a second, forward-looking one: where is this price heading.

It ingests public retail price data, records every change rather than overwriting it, transforms it into tested business marts, and serves those marts to an API, an alerting path, a BI dashboard and an LLM-written brief. All six planned phases are complete and running locally.

5Database design

PostgreSQL 16 with the pgvector extension. Twelve tables in three groups: reference data, event history, and derived output.

5.1Invariants enforced by the database

These are not conventions — the schema rejects violations, so no application bug can break them.

InvariantMechanismWhy it matters
Exactly one open version per productPartial unique index on product_versions(product_id) where is_currentSCD2's core promise; a double-open row would make "current title" ambiguous
No duplicate observationsUnique index on (idempotency_key, observed_at)Retries and replays collapse instead of inflating history
A match is an unordered pairCheck constraint product_id_a < product_id_bPrevents the same claim being stored twice and disagreeing with itself
History is append-onlyNo UPDATE path in application code for event tablesLate or corrected data adds a row; it never rewrites the past
Events stay queryable at volumeMonthly range partitions on observed_at, created on demand115 partitions currently in use, spanning 2010–2026

7Warehouse layer

dbt Core on PostgreSQL, in three layers. Every consumer — the API, alerting, forecasting, the dashboard and the AI brief — reads marts. None reads the raw event tables. That is what keeps a business rule defined once.

LayerModelsPurpose
staging/6 viewsCast and clean the serving tables. Currency is uppercased and always retained.
intermediate/3 viewsThe single join every mart needs; collapse to one price per product/retailer/currency/day; add staleness.
marts/5 tablesBusiness questions, materialized because they are queried repeatedly.
The five marts and the question each answers
MartAnswersRows
mart_price_trendDaily series and day-over-day change; feeds forecasting8,433
mart_price_volatilityWhich SKUs move most, by coefficient of variation272
mart_price_gap_vs_ownCompetitor price versus our catalogue, matched on barcode152
mart_undercut_alertsWho is undercutting us, how badly, how fresh the evidence108
mart_out_of_stock_frequencyOut-of-stock rate per SKU and retailer0
Currency is part of the grain everywhere. The data spans 24 currencies. Comparing across them without dated exchange rates would produce authoritative-looking nonsense and fire false undercut alerts — 12 SEK beside 1.20 EUR reads as a catastrophic undercut when the two are close in value. The gap mart therefore joins on barcode and currency; a cross-currency pair produces no row rather than a wrong one. Coefficient of variation is the headline volatility metric precisely because it is unitless and survives this. See ADR-008.

Delivery is at-least-once by design: acks_late with reject_on_worker_lost means a crashed worker's task re-runs rather than vanishing. Duplicate work is harmless because every event carries an idempotency key.

8.1Rate limiting

Two independent guards, both in Redis so the limit holds across every worker process — Celery's own rate_limit is per-worker and would silently triple the request rate if three workers ran. A token bucket smooths the instantaneous rate; a daily counter enforces published quotas such as eBay's documented 5,000 calls per day. Quota exhaustion does not retry, because the quota resets tomorrow and retrying today cannot succeed; the task dead-letters immediately.

10Data sources

SourceAuthStatusRole

Adding a keyed source is a single new file implementing the SourceClient interface. The ingestion pipeline, CDC, marts, forecasting and alerting require no changes — that separation was the reason for starting with keyless sources (ADR-000).

All data is real, with one exception. Every price, product, retailer and date comes from the Open Prices API and is stored raw before parsing. The single authored dataset is dbt/seeds/own_catalog.csv, which stands in for the company catalogue the platform compares against. It is generated from products actually observed in the last 60 days, with our price set around each observed market average. Its provenance is documented in dbt/seeds/README.md.

11Testing and quality

SuiteCountCovers
Python unit~130Normalizers, CDC rules, forecasting metrics, guardrail, alert logic, auth
Python integration~20Real Redis rate limiting; CDC parity against a real database
dbt data tests102Schema, referential integrity, ranges, and cross-field invariants
Terraform—fmt and validate, run without AWS credentials

Two testing choices worth knowing about:

  • dbt tests assert cross-field invariants, not just column constraints. The price gap must agree with its own inputs; the undercut flag must agree with the gap; maximum must exceed minimum; time must move forward within a series. A not_null test would catch none of those, and each guards against a refactor silently flipping a sign.
  • The two CDC implementations are tested against each other. A row-by-row path and a set-based path both exist; the set-based one is roughly 290× faster over a high-latency link. A parity test runs both over the same dataset and asserts identical output, covering late arrival, heartbeat boundaries, duplicates and multi-retailer days. If they ever drift, the build fails.

12.2Recovering a lost database

This procedure was executed for real during development, after a Docker storage fault destroyed the volume.

docker compose up -d
.venv/Scripts/python.exe -m alembic upgrade head
python -m app.cli replay openprices 2026-08-29   # repeat per stored day
python -m app.cli seed openprices --tier 1       # replay restores events, not seeds
make dbt-build

Rebuild took 30 seconds for 3,420 events and made no upstream API calls. Note the second-to-last line: replay restores price history but not the seed configuration, which is a manual step people forget.

13Known limitations

These are stated plainly rather than discovered later. None is a defect in the code.

  1. The out-of-stock mart returns zero rows. No connected source publishes availability. Resolved by connecting Best Buy or Digi-Key; no code change required.
  2. Only 11 of roughly 50 series are fresh enough to forecast. Crowd-sourced prices are sparse. All three models sit within 0.01 percentage points of each other and the naive baseline wins 8 of 11 series — retail prices are close to a random walk on short series. This is an honest result, not a tuning failure; a daily-refresh retail API is what would make forecasting genuinely useful.
  3. Terraform has never been applied. fmt and validate pass; plan has not run. Only syntax and provider schema are confirmed. Expect a first apply to surface real issues — availability zones, engine version drift, IAM propagation.
  4. The CrewAI narration path has not run against a live model. No LLM credential is configured. The brief renders deterministically, and the numeric guard and its fallback are tested independently.
  5. Email delivery is built but unproven against a real mail server. SMTP and SES channels exist and are unit-tested with mocks; neither has sent a message to a live relay, because no credentials are configured.
  6. 2,187 match candidates await review. That is a genuine human workload. Raising the review threshold above 0.80 reduces it at the cost of recall; the stored reviewer verdicts are what would let that be tuned with evidence.
  7. ADR numbering has gaps (002–004 were never written). Documentation debt, noted rather than renumbered, since the existing numbers are referenced from code comments.

14Decision log

000Build local-first from keyless sources, so the pipeline is proven before any API key is a blocker
001Use Open Prices rather than plain Open Food Facts — it carries real prices, dates and store locations
005Celery Beat rather than an orchestrator; Airflow or Dagster when DAG lineage and asset-aware backfills are needed
006Docker runs the stateful services only; workers run from the virtual environment
007Add a set-based CDC path for bulk loads, keeping the row-by-row one as the tested reference
008Never compare prices across currencies; currency is part of the grain everywhere
009Score forecasts on observed days only, and refuse to forecast stale series
010The weekly brief is deterministic by default; the LLM must pass a numeric guard or be discarded
011Write the infrastructure, do not apply it

16Recommended next steps

  1. Obtain a Best Buy API key. Highest value per unit of effort: it is the easiest approval, it publishes stock data — which alone activates the out-of-stock mart — and its six-hourly refresh cadence gives forecasting the dense daily series it currently lacks. Two of the six known limitations close together.
  2. Run terraform plan against a real account before committing to a deployment date. The configuration is validated but unproven; budget for a first-apply debugging session.
  3. Work the match review queue to a few hundred labelled pairs, then measure precision and recall. Only then tune the 0.80 threshold — the stored verdicts exist precisely so this can be evidence-led.
  4. Add dated FX rates if cross-currency comparison is ever required. The upgrade is additive: an fx_rates table, a converted column in the intermediate layer, and currency-agnostic marts alongside the scoped ones. No existing model needs rewriting.
  5. Move to an orchestrator only when backfill lineage across interdependent jobs becomes the pain point. Beat is sufficient for periodic polling and materially simpler to operate.
